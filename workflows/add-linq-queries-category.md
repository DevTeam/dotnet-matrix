# Add the LINQ Queries category

This document is the self-contained handoff for implementing the `linq-queries`
category. It carries every decision already taken, every API fact already
verified against the real packages, and the exact remaining work. It is written
so that a human or an LLM can finish the category in a fresh chat without
recovering any undocumented history.

Read it together with, and subordinate to:

- [add-category.md](add-category.md) — the general category workflow and the
  **LLM execution policy**. That document wins on anything procedural.
- [rating.md](rating.md) — the scoring rule, which constrains the scenario set.
- [category-roadmap.md](category-roadmap.md) — where the finished category is
  recorded.

## Starting a separate chat

```text
Finish the LINQ Queries category in dotnet-matrix.

Read workflows/add-linq-queries-category.md completely; it is the handoff for

re-derive. Read workflows/add-category.md as the procedural source of truth and
workflows/rating.md for the scoring rule.

The project shell src/Matrix.LinqQueries already exists and builds in both
MatrixMode variants. Continue from "Remaining work" in the handoff.

Do not run benchmarks.
```

## LLM execution policy (restated because it is easy to miss)

An LLM **must not** run `linq-queries-benchmarks` (including `--smoke`),
`linq-queries-update-library`, `prepare-commit`, `ci-reports`, `reproduce`, or
the benchmark executable directly. BenchmarkDotNet runs are long and make the
workstation unresponsive. After validation passes, stop and hand the user the
commands in [Commands for the user](#commands-for-the-user).

### Why the two rating flags are what they are

- **`HandCoded` must stay `MatrixRating=false`.** `rating.md` states that a
  non-rated library does not define `best`. A hand-written loop costs near zero
  time and zero allocations in most of these scenarios; letting it define `best`
  would annihilate every score, which is the documented failure of
  `DependencyInjection / Prepare`. `HandCoded` also carries the single
  BenchmarkDotNet `[Benchmark(Baseline = true)]` attribute — only one per class
  is allowed.
- **`System.Linq` must stay `MatrixRating=true`, set explicitly.** For a
  package-less baseline `MatrixRating` defaults to `false`. System.Linq is the
  reference every one of these libraries exists to beat; the reader's actual
  question is "does StructLinq beat plain LINQ". Removing it from the rating
  would remove the only meaningful reference.

Two package-less baselines in one category is new for this repository.
`MatrixMetadata` permits it (it constrains only uniqueness of library id,
primary package and code name), but confirm that
`MatrixBenchmarkRunner.IncludeBaselines` and the README/chart renderers handle
two baselines before trusting the first generated report.

## 3. Contract rules that apply to every scenario

These five rules are the substance of the category. Put them in the Scope
preamble of `workflows/feature-contracts/linq-queries.md`, rules 1 and 2 in bold.

1. **LINQ is lazy, so every scenario ends in a terminal operation.** Returning an
   unenumerated query, or any lazy type belonging to the compared library, is a
   contract violation: it would measure query *construction* and produce a
   plausible-looking wrong number. Every benchmark method returns a concrete type
   — `int`, `bool`, `int[]`, `List<int>`, `Order`, `RegionTotal[]`,
   `CustomerOrder[]` — never `object` and never `IEnumerable<T>`. BenchmarkDotNet
   consumes the returned value, which defeats dead-code elimination.
2. **Scenarios 1–17 use ordinary non-capturing static lambdas for every library,
   without exception.** Struct predicates appear only in scenario 18, and there
   for every library that has them. Writing StructLinq with a struct predicate
   and System.Linq with a lambda in the same cell would compare two different
   programs. A non-capturing `static n => n % 3 == 0` is cached by the compiler in
   a static field, so no delegate is allocated for anybody — that is the fair
   common denominator. A capturing lambda would add closure noise unrelated to
   query machinery.
3. **Expected values are computed by hand-written loops** in
   `QueryExpectations.cs`, never through `System.Linq`. System.Linq is a compared
   library here; making it the oracle for its competitors is circular. This is
   also forced by the `Using Remove="System.Linq"` decision in §5.1.
4. **Fixtures are built in the static initializer of `QueryData`, outside any
   measured method.** A benchmark class holds a `private readonly` field copied
   from `QueryData`, exactly as `ReadLargeDataset` holds
   `private readonly string _csv = CsvData.LargeCsv;` in `Matrix.CsvProcessing`.
   No benchmark builds or copies its input.
5. **Hand-coded does the same logical work** — same predicate, same
   materialization — and does not exploit knowledge of the data. Pre-sizing a
   `List<T>` or array where the count is genuinely known is fair; skipping work
   the libraries must do is not.

### Fixtures (`QueryData.cs`)

| Fixture | Type | Size | Definition |
| --- | --- | ---: | --- |
| `Numbers` | `int[]` | 10 000 | `(i * 37) % 1000` — 1 000 distinct values, each 10 times (37 is coprime with 1000) |
| `NumberList` | `List<int>` | 10 000 | the same values |
| `ScanNumbers` | `int[]` | 10 000 | `(i * 37) % 500`, then `ScanNumbers[9_500] = 777` — the only value ≥ 700 |
| `Batches` | `int[][]` | 500 × 20 | `((b * 20 + k) * 37) % 1000` |
| `Orders` | `Order[]` | 5 000 | `Id = i+1`, `CustomerId = (i % 500)+1`, `Region = Regions[i % 8]`, `Amount = ((i * 1237) % 5000)+1`, then `Orders[4_500]` amount overwritten to `10_000` |
| `Customers` | `Customer[]` | 500 | `Id = i+1`, `Name = "Customer" + Id` |
| `Regions` | `string[]` | 8 | `North, South, East, West, Nordic, Alpine, Baltic, Iberia` |
| `Opaque()` | `IEnumerable<int>` | 10 000 | C# iterator over the same values |

Deliberate choices — do not "simplify" these:

- **`Amount` is `int`, not `decimal`.** Decimal arithmetic would cost more per
  element than the query machinery under measurement.
  `((i * 1237) % 5000) + 1` yields 5 000 **unique** amounts in 1..5000.
  Uniqueness is required so `OrderedTopN` has no ties: `System.Linq` ordering is
  documented stable, StructLinq's and LinqAF's are not. The largest region total
  is about 25 million, comfortably inside `int`.
- **`ScanNumbers` is separate from `Numbers`.** On `Numbers` a "rare value"
  predicate first matches at `i = 27`, so `AnyMatch` would measure nothing. The
  sentinel at index 9 500 forces a 95 % scan.
- **`Orders[4_500].Amount = 10_000`** is one sentinel serving two scenarios:
  `FirstMatch` (a 90 % scan) and `OrderedTopN` (a unique deterministic maximum).
- **`Opaque()` exposes no `ICollection<T>`, no `Count` and no indexer**, so no
  library can take an array fast path. It allocates one state machine per
  enumeration for every library equally; that shared floor compresses the memory
  spread in `OpaqueSource` and must be stated in the contract.

## 4. Verified API facts

**Established by reflection over the complete exported surface of the real
packages and by compiling against them. Do not re-derive, and do not trust the
libraries' own documentation over this table — three of these findings contradict
it.**

| Operator | System.Linq | ZLinq 1.5.6 | StructLinq 0.28.2 | Hyperlinq 3.0.0-beta9 | LinqAF 3.0.0 |
| --- | :-: | :-: | :-: | :-: | :-: |
| `Where`, `Select`, `SelectMany`, `Distinct` | ✔ | ✔ | ✔ | ✔ | ✔ |
| `Take`, `Skip`, `Any`, `All`, `First(OrDefault)` | ✔ | ✔ | ✔ | ✔ | ✔ |
| `Count`, `ToArray`, `ToList` | ✔ | ✔ | ✔ | ✔ | ✔ |
| `Sum`, `Aggregate`, `Min`, `Max` | ✔ | ✔ | ✔ | **ABSENT** | ✔ |
| `Average` | ✔ | ✔ | **ABSENT** | **ABSENT** | ✔ |
| `OrderBy`, `OrderByDescending` | ✔ | ✔ | ✔ | **ABSENT** | ✔ |
| `Zip` | ✔ | ✔ | ✔ | **ABSENT** | ✔ |
| `GroupBy` | ✔ | ✔ | **ABSENT** | **ABSENT** | ✔ |
| `Join` | ✔ | ✔ | **ABSENT** | **ABSENT** | ✔ |
| `ReadOnlySpan<T>` source | **ABSENT** | ✔ | **ABSENT** | ✔ | **ABSENT** |
| struct predicate (non-delegate) | **ABSENT** | **ABSENT** | ✔ | **ABSENT** | **ABSENT** |

Three of these corrected an earlier assumption and are the reason this section
exists:

1. **Hyperlinq 3.0.0-beta9 has no aggregation at all except `Count`.** No `Sum`,
   `Aggregate`, `Average`, `Min` or `Max`. This is why the canonical terminal
   operation across the category is `Count`/`ToArray` and not `Sum`; see §5.2.
2. **StructLinq does have `Zip`** (2 overloads) and `Aggregate` and `Sum`.
3. **StructLinq has no span entry point.** `ToStructEnumerable` requires `T[]`,
   `List<T>` or `IEnumerable<T>`.

### Entry points and call shapes, as actually compiled

| Library | Per-file using | Entry | Verified working |
| --- | --- | --- | --- |
| System.Linq | `using System.Linq;` | — | idiomatic method syntax |
| ZLinq | `using ZLinq;` | `.AsValueEnumerable()` | 16 of 16 probed operators, including span, `GroupBy`, `Join`, `Zip` |
| StructLinq | `using StructLinq;` | `.ToStructEnumerable()` | `Where`, `Select`, `Count`, `Sum`, `Aggregate`, `ToArray`, `ToList`, `Take`, `Skip`, `Any`, `First`, `Distinct`, struct predicate |
| Hyperlinq | `using NetFabric.Hyperlinq;` | `.AsValueEnumerable()` | `Where`, `Select`, `Count`, `ToArray`, `ToList`, `Take`, `Skip`, `Any`, `First`, `Distinct`, opaque source |
| LinqAF | `using LinqAF;` | extension methods directly on `int[]`, `List<T>`, `IEnumerable<T>` | all 17 probed operators, including `GroupBy`, `Join`, `Zip` |

Shapes that needed more than the obvious call:

- **ZLinq, aggregate inside a group.** `g` is an `IGrouping`, so the inner fold
  needs its own entry point:
  `.Select(static g => new RegionTotal(g.Key, g.AsValueEnumerable().Sum(static o => o.Amount)))`
- **StructLinq takes plain `Func<T,bool>`, not `in` parameters.**
  `static (in int n) => ...` fails with CS1677.
- **StructLinq `Select` and most projecting operators need the `x => x` type-hint
  argument**: `.Select(static n => n * 2, x => x)`.
- **StructLinq struct predicates must be passed by `ref`:**

  ```csharp
  internal readonly struct DivisibleByThree : IFunction<int, bool>
  {
      public bool Eval(int element) => element % 3 == 0;
  }

  var predicate = new DivisibleByThree();
  return source.ToStructEnumerable().Where(ref predicate, x => x).Count();
  ```

- **StructLinq `SelectMany`, `Zip`, and `OrderByDescending` compile with the
  idiomatic overloads on the concrete struct enumerable.** `Zip` returns tuples,
  which are projected to products before materialization.
- **Hyperlinq over an opaque sequence needs an explicit type argument:**
  `source.AsValueEnumerable<int>()`.
- **Hyperlinq span operators are extension methods directly on
  `ReadOnlySpan<T>`.** No `AsValueEnumerable` entry is needed.
- **Hyperlinq 3.0.0-beta9 has no struct-function predicate API.** Reflection over
  both `NetFabric.Hyperlinq` and `NetFabric.Hyperlinq.Interfaces` exposes only
  delegate-based `Where` overloads (`Predicate<T>` and indexed/async delegates).
  Scenario 18 is therefore `Unsupported` for Hyperlinq.
- **Hyperlinq's `IFunction<,>` is not in the `NetFabric.Hyperlinq` namespace.** It
  lives in the transitive `NetFabric.Hyperlinq.Interfaces` package; find the real
  namespace before writing scenario 18.

### Previously unresolved — resolved by compilation

- StructLinq `SelectMany`, `Zip`, and `OrderByDescending` compile through their
  idiomatic concrete-enumerable overloads.
- Hyperlinq `ReadOnlySpan<T>` uses direct span extensions; `SelectMany` compiles
  when the selector returns the inner array's value enumerable.
- Hyperlinq exposes no struct-predicate overload, so scenario 18 has an explicit
  `[FeatureUnavailable]` declaration.

### 5.2 Why the canonical terminal operation is `Count`/`ToArray`

Hyperlinq beta9 has no `Sum` (§4). Had the filtering, projection and source-shape
scenarios all terminated in `Sum`, Hyperlinq would have been `Unsupported` in six
of eighteen scenarios and the rating would have measured the choice of terminal
operation rather than the library. Summation is therefore isolated into a single
dedicated `Aggregate` scenario, where Hyperlinq is honestly `Unsupported` once.

### 5.5 Hand-coded scenario 18

Implement as a struct-constrained generic, which is what the struct libraries do
and what the JIT monomorphizes:

```csharp
private static int CountWhere<TPredicate>(int[] source, TPredicate predicate)
    where TPredicate : struct, INumberPredicate
```

with `readonly struct DivisibleByThree : INumberPredicate`. The constraint is
devirtualized and inlined, so this is not "interface dispatch added for matrix
infrastructure" — it is the semantics under test. Because `HandCoded` is not
rated, this cell never defines `best`.

### 5.6 Why this scenario set is defensible under `rating.md`

Write this reasoning into the contract as a "Rating fairness" section, and record
the same points in `category-roadmap.md` open items. A reader who feels wronged
should find the case stated, not have to discover it.

- The maximum is `200 × 18 = 3600`. "Breadth is paid for": an unsupported
  scenario costs its full 200 points, and the `Scenarios` column shows coverage.
- A 67 % ceiling for the narrowest library is far gentler than cases already
  published — ZLogger enters 3 of 8 Logging scenarios (37 %) and MvvmCross 6 of
  15 in Dependency Injection (40 %).
- Ordering, grouping and joining are the first operators anyone evaluating a
  "LINQ replacement" looks for. Not measuring them would hide the most important
  thing a reader needs before adopting StructLinq or Hyperlinq. One scenario per
  operator is the smallest honest representation.
- The countervailing force is memory, which is half of every scenario's points.
  In scenarios 1–13 the struct libraries should report **0 B** where System.Linq
  and LinqAF allocate, so they can take the memory half of scenarios System.Linq
  cannot. The category is not a foregone conclusion.
- **The known soft spot:** scenario 18 has only one rated entrant (StructLinq)
  and scenario 7 only two rated entrants (ZLinq, Hyperlinq). This is exactly
  `rating.md` §"Scenarios with one entrant". Two of eighteen (11 %) is at the
  level of JSON Serialization (2 of 14) and Validation (2 of 10).
- **There is no rating escape hatch.** The rating is computed over *every*
  scenario regardless of chart-group membership, so a "feature-only" scenario
  that does not affect the rating does not exist. The wording
  `Rating: feature-only` in `feature-contracts/csv-processing.md` is a leftover
  from the previous medal rule.
- Deliberately excluded, and to be recorded as decisions rather than omissions:
  `GroupJoin` (the same entrants as `JoinLookup`), `ToDictionary` (measures
  mostly `Dictionary<K,V>`), `Union`/`Intersect`/`Except`, `Chunk`, `Average`,
  and asynchronous variants.

## 7. Validation

`QueryChecks.cs` at the project root, mirroring
`src/Matrix.CsvProcessing/CsvChecks.cs`: an `internal static class` with one
`[Conditional("MATRIX_VALIDATION")]` method per feature, the explicit library id
as the first parameter, calling `MatrixValidation.Require(library, condition, message)`.
Checks are invoked **inside** the benchmark method on the result before returning
it, so they compile away entirely in `MatrixMode=Benchmark`.

Pass the library id explicitly — `QueryChecks.FilterCount(LibraryCatalog.ZLinq, result)` —
so accidental cross-library validation is detected and errors are attributable.

For large results use the `CsvChecks.Large` shape — length, first element, last
element, checksum — rather than thousands of individual `Require` calls, because
the runner executes every benchmark three times.

**Order-insensitive checks are mandatory for `DistinctValues`,
`GroupByAggregate` and `JoinLookup`.** Output order is not contractually the same
across five implementations: System.Linq preserves first-occurrence and outer
order, the others need not. Compare a sorted copy; sorting inside a
`[Conditional]` check costs nothing in benchmark mode. An order-sensitive
assertion here would produce a spurious `Failed` that looks like a real defect.

Key assertions: 9 — `true`; 10 — `Id == 4_501 && Amount == 10_000`; 15 —
length 20, `[0] == 4_501`, element-wise equality; 16 — length 8, a copy sorted by
region ordinal equals the expectation; 18 — the result is **identical** to
scenario 1's, which proves the struct predicate is semantically the same
predicate as the lambda.

**Do not add a runtime allocation assertion to scenario 18.**
`GC.GetAllocatedBytesForCurrentThread()` deltas are not reliably zero on the
runner's first iterations because of JIT and tiered compilation, and a flaky
`Failed` is worse than no assertion. Support is defined by the presence of the
library's documented struct-function API, and the memory column of the published
report is the evidence.

## 8. Risks

### 8.1 LinqAF versus `System.Linq` — mitigated, keep it mitigated

`ImplicitUsings=enable` injects `global using System.Linq;` into every file.
LinqAF's extension methods have the same names and receiver types, so any file
with both in scope fails with CS0121 on `Where`, `Select`, `ToArray` and the rest.

The csproj already carries the fix:

```xml
<ItemGroup>
    <!-- LinqAF redeclares the System.Linq extension methods, so the implicit
         using would make every call ambiguous. System.Linq is imported per file. -->
    <Using Remove="System.Linq"/>
</ItemGroup>
```

**This is verified working**: LinqAF compiles all 17 probed operators, including
`GroupBy`, `Join` and `Zip`, with no ambiguity.

Consequences to plan for:

- `QueryData.cs`, `QueryExpectations.cs`, `QueryChecks.cs` and the models must be
  written with hand loops. No `Enumerable.Range`, no `.ToArray()`, no
  `.OrderBy()`. Contract rule 3 requires this anyway, so it costs nothing.
- `Benchmarks/SystemLinq/*.cs` are the **only** files that carry
  `using System.Linq;`.
- The IDE will offer to add `using System.Linq` on every red squiggle. Reject
  those in non-`SystemLinq` files; one stray import turns a whole file into
  CS0121.
- Global usings do not cross an assembly boundary through `ProjectReference`, so
  `src/Matrix` is unaffected.
- Fallback if `Using Remove` ever misbehaves: `<ImplicitUsings>disable</ImplicitUsings>`
  plus a fully explicit `GlobalUsings.cs`.

### 8.2 LinqAF is a 26 MB assembly, last released in 2019

BenchmarkDotNet copies the whole build output for each build partition, so
benchmark builds and CI temp usage grow noticeably. The very large generic
surface also lengthens compilation. Measure it once and note the figure. If
something becomes untenable, record the reason and raise the question of dropping
the library explicitly — never silently.

### 8.3 Hyperlinq is a prerelease with a packaging defect

- The exact literal pin `3.0.0-beta9` restores deterministically and satisfies
  `MatrixMetadata`, which rejects only `$()`, `*`, `[`, `]`, `(`, `)` and `,`.
- `netstandard2.1` is a supported asset for `net10.0`; restore is clean with no
  `NU1701` and no vulnerability warnings.
- The undeclared `Microsoft.Bcl.AsyncInterfaces` dependency is handled in §2.
- Its published API does not match its documentation. §4 is the authority.
- `MatrixDescription` already records the prerelease status, because the Web
  catalog and README are where a reader decides whether to adopt it.

### 8.4 StructLinq has not been released since 2022

Functionally fine, but the API leans hard on type inference and frequently needs
the `x => x` type-hint argument and `ref` struct-predicate overloads. Expect
several compile iterations. `MatrixDescription` records the release status.

### 8.5 Laziness and JIT dead-code elimination

Covered by contract rule 1. Scalar scenarios return `int`/`bool`, which
BenchmarkDotNet's `Consumer` handles without `DeadCodeEliminationHelper`. Cheap
scenarios stay above the noise floor: `AnyMatch` scans 9 500 elements,
`FirstMatch` 4 500, `PagedSlice` materializes 1 000. The `rating.md` pathology of
a preparation scenario measuring 0 ns does not arise in this category.

### 8.6 Struct-predicate contamination

The tempting mistake is to write the StructLinq benchmarks with struct
predicates in scenarios 1–17 "because that is how you would really use them".
That silently compares different programs in the same cell. Contract rule 2
forbids it; put it on the review checklist.

### 8.7 BenchmarkDotNet code generation against `Using Remove`

The runner passes `/p:MatrixMode=Benchmark` and BenchmarkDotNet generates and
builds its own harness project referencing ours. `<Using Remove="System.Linq"/>`
applies only to our project, but this combination has never been exercised in
this repository, and an LLM cannot verify it because benchmarks are forbidden.
This is why the user runs `linq-queries-benchmarks --smoke` first.

## 12. Commands for the user

Hand these over, in this order, and do not run them yourself:

```bash
dotnet run --project build/build.csproj -- linq-queries-benchmarks --smoke
dotnet run --project build/build.csproj -- linq-queries-benchmarks
dotnet run --project build/build.csproj -- finalize-commit
```

The `--smoke` run — one warmup, one iteration, one invocation — is not optional
advice. It is the only cheap way to exercise BenchmarkDotNet's generated-harness
build against `<Using Remove="System.Linq"/>` and the 26 MB LinqAF copy before
spending a full measured run. `finalize-commit` then regenerates `README.md`, the
PNG charts and the Web data from the existing reports without re-running
benchmarks.
